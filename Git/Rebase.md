Есть основная (базовая) ветка dev, и созданная от неё текущая - feature.

`rebase` берёт коммиты текущей ветки (в моём случает feature), которых нет в новой базовой ветке (dev), и заново применяет их поверх этой новой базы в том же порядке. В результате создаются коммиты с новыми хэшами.

Когда ты ввел команды:

```bash
git checkout feature
git rebase dev
```

Твоей текущей веткой стала `feature`, а ветка `dev` выступила в роли новой базовой ветки.

Согласно твоему же (абсолютно верному!) определению: Git взял коммиты из текущей ветки (`feature`), перенес их и заново применил к новой базе (`dev`).

## В чём же тогда был подвох?

Подвох в том, внутри какой ветки физически произошли эти изменения.

Поскольку ты находился на ветке `feature`, Git изменил именно её! Он перестроил историю `feature` так, будто ты только что отпочковался от самого свежего коммита `dev`.

А вот сама ветка `dev` в этот момент осталась стоять на месте. На ней не появилось ни одного нового коммита, её указатель в `.git/refs/heads/dev` не сдвинулся ни на миллиметр. Ты изменил прошлое ветки `feature`, но никак не повлиял на настоящее ветки `dev`.

## Как это выглядит на схеме:

До ребейза:  
Ветка `dev` ушла вперед, а ты сидишь в своей `feature` со старым основанием.

```text
          A --- B (ветка dev)
         /
--- C1 -- 
         \
          F1 --- F2 (ветка feature)
```

После того, как ты запустил `git rebase dev` (находясь на `feature`):  
Git взял твои коммиты `F1` и `F2` и переприменил их от коммита `B` (нового основания). Обрати внимание, где теперь находится `dev`, а где `feature`:

```text
          A --- B (ветка dev — осталась ТАМ ЖЕ!)
                 \
                  F1* --- F2* (ветка feature — изменилась и переехала!)
```

## Так где же скрывается проблема «публичной ветки»?

Проблема в букве `*` (звёздочке) у коммитов `F1*` и `F2*`.

Если до этого ребейза ты уже успел отправить старые коммиты `F1` и `F2` на GitHub (сделать `git push`), то на GitHub сейчас лежит старая история.  
Когда ты локально сделал rebase, твои коммиты превратились в совершенно новые `F1*` и `F2*`.

Теперь твоя локальная ветка `feature` и ветка `feature` на GitHub — это две разные истории. Чтобы залить изменения, тебе придется перезаписать GitHub силой (`push --force`). А если твой коллега в этот момент уже скачал себе старые `F1` и `F2`, его Git при следующей синхронизации попытается соединить их с новыми `F1*` и `F2*`. Начнется хаос из дубликатов кода и конфликтов.

Золотое правило звучит так: никогда не делай rebase ветки `feature`, если её уже скачал кто-то кроме тебя.

## А как же тогда передать коммиты в `dev`?

Чтобы твои новые коммиты `F1*` и `F2*` наконец-то попали в ветку `dev`, нужно сделать второй шаг — влить их туда. Так как теперь `feature` аккуратно растет прямо из кончика `dev`, это делается мгновенно через Fast-Forward:

```bash
git checkout dev
git merge feature
```

И вот теперь указатель `dev` просто переместится вперед на коммит `F2*`. История станет идеально ровной и линейной!

Стало ли теперь понятнее, почему rebase меняет именно ту ветку, на которой ты стоишь, а не ту, чье имя ты указал в команде? Если хочешь, мы можем закрепить это на примере того, как безопасно обновлять свою ветку с помощью rebase, если ты работаешь один.

---

Сделал reabse публичной ветки, запушил с флагом --force, а у коллеги в локальном реп. остались старые коммиты. Что в таком случае делать? :)

Бывает, это классическая «аварийная» ситуация в разработке. Самое главное — коллеге ни в коем случае нельзя делать обычный `git pull`, иначе его Git попытается слить старую и новую истории, породив кучу дубликатов и конфликтов.

Поскольку ты уже переписал историю на сервере, коллеге нужно принудительно синхронизировать свою локальную ветку с новым состоянием на сервере.

Способ исправления зависит от того, успел ли твой коллега написать какой-то свой новый код в эту ветку, пока ты делал rebase, или он просто скачал её ранее и ничего не менял.

## Сценарий 1: Коллега просто скачал ветку и ничего своего не писал

Это самый простой и безболезненный случай. Коллеге нужно просто выбросить свою старую локальную историю ветки `feature` и заново забрать её с сервера.

Пусть коллега выполнит у себя в терминале:

```bash
git fetch origin
git checkout feature
git reset --hard origin/feature
```

- Что происходит физически: Команда `fetch` скачивает новые коммиты (твои перебазированные `F1*` и `F2*`) в локальный слепок сервера. А команда `reset --hard` жестко переставляет указатель локальной ветки коллеги на этот слепок. Старые коммиты `F1` и `F2` на его компьютере стираются, рабочая директория обновляется. История снова синхронизирована!

---

## Сценарий 2: Коллега успел написать свои коммиты поверх старой ветки

Это более сложная ситуация. Допустим, на сервере были коммиты `A` и `B`. Ты сделал rebase, и они превратились в `A*` и `B*`. Но коллега локально успел написать поверх старых коммитов свой коммит `K`.

Если он сделает `reset --hard`, его коммит `K` сотрется. Чтобы спасти его работу, коллеге нужно сделать rebase своего коммита на твою новую историю:

```bash
git fetch origin
git rebase --onto origin/feature origin/feature@{upstream} feature
```

_Звучит страшно, но давай разберем эту команду `--onto` («перенести на»):_  
Мы говорим Гиту коллеги: «Возьми ветку `feature`, найди коммиты, которые коллега написал поверх старой серверной версии (`origin/feature@{upstream}`), и перенеси их на новую серверную версию (`origin/feature`)».

## Альтернативный (более простой «человеческий») путь для Сценария 2:

Если команда `--onto` пугает, коллега может сделать проще и нагляднее:

1. Сохранить свой коммит в виде временной ветки: `git branch temp-save`
2. Сбросить основную ветку к серверу (как в Сценарии 1):
    
    ```bash
    git checkout feature
    git reset --hard origin/feature
    ```
    
3. Забрать свой коммит обратно с помощью хирургического переноса:
    
    ```bash
    git cherry-pick temp-save
    ```
    
    _(Git возьмет изменения из сохраненного коммита коллеги и аккуратно применит их поверх твоей новой истории)._
1. Удалить временную ветку: `git branch -D temp-save`
