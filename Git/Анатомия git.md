## 1. Как Git хранит файлы и папки

Git не сохраняет изменения (диффы), как некоторые другие системы контроля версий. Он сохраняет полные снимки (слепки) твоих файлов. Для этого он использует три основных типа объектов, которые лежат в скрытой папке `.git/objects`:

- Blobs (Блобы / Бинарные данные): Когда ты сохраняешь файл, Git берет его содержимое, сжимает его и превращает в объект-блог. Имя этого объекта — это уникальный хэш-код (SHA-1), вычисленный по содержимому файла. Обрати внимание: блоб хранит _только текст или данные_, он даже не знает имени твоего файла.
- Trees (Деревья): Этот объект представляет собой папку (директорию). Внутри файла-дерева записан список: имена файлов, их хэш-коды (ссылки на блобы) и ссылки на другие подпапки (другие деревья).

## 2. Что физически представляет собой сам коммит?

Сам объект коммита — это тоже простой текстовый файл, сжатый с помощью zlib. Если его «распаковать», ты увидишь структурированный текст, в котором записано всего несколько строчек:

1. Ссылка на дерево (`tree`): Хэш-код главного дерева (корневой папки твоего проекта). Зная этот хэш, Git может восстановить абсолютно все файлы и папки в том виде, какими они были в момент коммита.
2. Ссылка на родителя (`parent`): Хэш-код (или коды) предыдущего коммита, на основе которого сделан этот. Так выстраивается история. У самого первого коммита в репозитории этой строчки нет.
3. Автор (`author`): Имя, email и точное время (таймстемп), когда код был написан.
4. Коммитер (`committer`): Имя, email и время, когда коммит был непосредственно создан (иногда автор и коммитер — это разные люди, например, при применении чужого патча).
5. Сообщение коммита: Текст, который ты пишешь после флага `-m`.

## Пример «анатомии» коммита

Если заглянуть внутрь объекта коммита с помощью команды `git cat-file -p <хеш_коммита>`, ты увидишь примерно следующее:

```text
tree 92a51e6375f4f852b492b3b0dfb2f1532822a16d
parent 5b1a3c8293751283e390df0381023d810f391aef
author Ivan Ivanov <ivan@example.com> 1792156800 +0300
committer Ivan Ivanov <ivan@example.com> 1792156800 +0300

Реализовал авторизацию пользователей
```

## Подведем итог

Физически коммит — это маленький файл-ссылка. «Зафиксировать состояние» означает:

1. Запомнить, как выглядели все файлы и папки на этот момент (создать `tree`).
2. Привязать к этому снимку имя автора, время и комментарий.
3. Добавить ссылку на предыдущий шаг истории.

### Про Blob

Термин Blob расшифровывается как Binary Large Object (большой бинарный объект). В компьютерном мире так называют любой массив «сырых» бинарных данных (картинка, текст, видео, скомпилированный код), который база данных хранит как единое целое, не вдаваясь в его внутреннее устройство.

В Git блоб — это физический файл на диске, в котором хранится только содержимое (контент) твоего файла, сжатое в специальный формат .git/objects.

Давай заглянем «под капот» и разберем, из чего он состоит и как создается.
## 1. Из чего состоит блоб (Анатомия)

У блоба в Git есть три уникальные особенности:

1. Там нет имени файла. Блоб не знает, как называется твой файл (`index.html`, `script.js` или `photo.png`). Он не знает, в какой папке лежит файл. Он хранит _только внутренности_.
2. Там нет прав доступа и дат. Информация о том, является ли файл исполняемым, когда он был изменен, тоже не пишется в блоб.
3. Его имя — это хэш-код. Файл блоба на диске называется сорокасимвольным хэшем (SHA-1), который вычисляется строго по его содержимому.

## 2. Как Git физически создает блоб (Пошагово)

Когда ты пишешь команду `git add main.py`, Git выполняет стандартный алгоритм, состоящий из двух фаз: создание блоб и обновление файла-индекса.

Создание блоб.

1. Формирует заголовок: Берёт слово `blob`, ставит пробел, указывает _размер файла в байтах_ и добавляет нулевой байт (маркер конца заголовка).
    
     Пример заголовка: `blob 24\0` (значит, это блоб размером 24 байта).
    
2. Склеивает с контентом: Соединяет этот заголовок с реальным текстом твоего файла.
3. Считает хэш (SHA-1): От получившейся строки вычисляется хэш-код. Например, получилось: `8a23425118742880029b35b6ab37c9f6d14902b1`.
4. Сжимает данные: Сжимает заголовок + контент с помощью алгоритма zlib (чтобы файл занимал меньше места).
5. Записывает на диск: Создает файл в папке `.git/objects/`.

Обновление индекса.

**Индекс в Git — это один-единственный бинарный файл, который называется `.git/index`**

**Обновляет файл `.git/index`:** Git открывает файл индекса и дописывает (или обновляет) в нем ровно одну строчку для этого файла.

Что внутри файла `.git/index`?

В отличие от коммитов или веток, файл индекса — **бинарный** (для максимальной скорости работы). Но если бы мы могли его прочитать, мы бы увидели, что он представляет собой плоский плотный список всех файлов твоего проекта.

Для каждого файла в индексе Git записывает:

- **Имя файла и путь к нему** (например, `src/main.py`).
- **Хэш блоба**, в котором сейчас хранится его содержимое (`7a5b3c...`).
- **Метаданные из операционной системы:** права доступа (права на чтение/выполнение), размер файла на диске, а также **время последнего изменения (mtime)** и **время создания (ctime)**.

Зачем нужны эти метаданные (mtime/ctime)?

Это главный секрет невероятной скорости Git. Индекс — это не просто черновик для коммита, это **кэш**.

Когда ты в следующий раз пишешь `git status`, Git не считывает заново все файлы проекта и не пересчитывает их хэши (это заняло бы кучу времени на больших проектах). Он просто мгновенно опрашивает файловую систему ОС и сравнивает текущее время изменения файла `src/main.py` на диске со временем, записанным в `.git/index`.

- Если время совпадает — файл не менялся. Git идет дальше.
- Если время отличается — Git понимает: «Ага, файл потрогали!». Только в этот момент он считывает его, считает новый хэш и, если хэш изменился, подсвечивает файл красным в `git status` как _Changes not staged for commit_.

## 3. Почему это гениально? (Свойства дедупликации)

Такой подход дает Git невероятную скорость и защиту от дублирования данных:

- Защита от дублей (Дедупликация): Если у тебя в проекте лежит 10 абсолютно одинаковых картинок в разных папках с разными именами, Git создаст всего один блоб. Потому что контент одинаковый, а значит, хэш-код будет один и тот же.
- Контроль целостности: Если на диске из-за сбоя повредится хотя бы один бит в файле, его хэш-код мгновенно изменится. Git сразу заметит это при проверке (`git fsck`) и поймет, что репозиторий «битый».

## Как это потрогать руками?

Ты можешь сам заставить Git создать блоб из любого текста в обход стандартного рабочего процесса, выполнив команду в терминале:

```bash
echo "Hello, world!" | git hash-object -w --stdin
```

Команда выдаст хэш (например, `af5626...`), сожмет строку "Hello, world!" и физически положит этот блоб в базу данных `.git/objects`. При этом никакого коммита или файла в твоей рабочей папке еще даже не существует!

Теперь понятно, почему блоб — это просто «слепая» коробка с данными? Именно поэтому Git нужны «деревья» (tree), о которых мы говорили раньше: ведь кто-то должен помнить, что блоб `af5626...` на самом деле называется `hello.txt` и лежит в корневой папке.

### Продолжение про логику работы git

_... git будет хранить изначальный файл и изменённый. Только в виде блоб, а коммиты - а ссылки на эти файлы._

Давай зафиксируем эту логику, чтобы картина стала кристально четкой:

1. Два файла на диске: Если у тебя был файл `readme.txt`, и ты изменил в нем хотя бы одну строчку, Git создаст новый, отдельный блоб для измененной версии. В базе данных `.git/objects` у тебя будут физически лежать два разных блоба: один со старым содержимым, другой — с новым.
2. Коммиты как ссылки: Первый коммит будет через объект «дерево» (tree) ссылаться на хэш _старого_ блоба. Второй коммит (измененный) будет ссылаться на хэш _нового_ блоба.

## Важный нюанс: Git не копирует то, что НЕ менялось

Благодаря хэшированию Git работает очень экономно. Если в твоем проекте лежит 100 файлов, а ты изменил только один:

- Git создаст только один новый блоб (для измененного файла).
- Новое «дерево» (tree) для свежего коммита будет содержать 99 ссылок на _старые_ блобы (которые не менялись) и только 1 ссылку на _новый_ блоб.

То есть файлы, которые не менялись, физически не дублируются. На них просто создается еще одна ссылка из нового коммита.

## Логичный вопрос: «Но ведь репозиторий тогда должен весить гигабайты из-за копий?»

Ты можешь подумать: _"Если я в файле размером 10 МБ изменю одну точку, Git создаст новый блоб на 10 МБ? Это же неэффективно!"_

И тут включается магия Git под названием Pack-файлы (упаковка):  
Периодически (или принудительно по команде `git gc`) Git запускает процесс оптимизации. Он смотрит на эти два блоба, понимает, что они очень похожи, и переписывает их. Он оставляет один файл целиком, а для второго вместо полной копии записывает только дельту (разницу). В итоге база данных сжимается до минимальных размеров, сохраняя при этом архитектурную целостность «снимков».

Теперь, когда физическая структура понятна, хочешь посмотреть, что такое ветка (branch) на физическом уровне? Спойлер: в Git это устроено еще проще, чем коммит, и весит всего 41 байт. Разберем?

### Подведем итог для `git add`

Команда `git add` — это подготовка **идеального слепка** будущего проекта.

1. Она берет текущую версию файла, упаковывает в `blob` и отправляет в хранилище.
2. Она связывает в файле `.git/index` путь к файлу (`src/main.py`) с хэшем этого нового блоба.

Когда ты наконец пишешь `git commit`, Git **вообще не смотрит на твою рабочую директорию (на твои файлы на диске)**. Он берет готовый файл `.git/index`, превращает его структуру в объекты `tree` (деревья) и создает коммит. Именно поэтому в коммит попадает только то, что было явно «добавлено» через `git add`.

## Более детальное описание работы команды `git commit`

Давай закрепим этот момент, разложив действия `git commit` по физическим шагам. Когда ты вводишь эту команду, Git берет данные из индекса (staging area), куда их бережно подготовила команда `git add`, и делает следующее:

1. Создает объекты «деревьев» (`tree`): Git смотрит на список файлов в индексе и превращает его в структуру папок и файлов. Он создает файлы-деревья для каждой измененной папки и одно главное `tree` для корня проекта. Для каждого дерева рассчитывается свой хэш SHA-1.
2. Узнает хэш родителя (`parent`): Git проверяет, на какой коммит сейчас указывает указатель `HEAD` (твое текущее положение в истории). Хэш этого коммита он берет в качестве родительского.
3. Собирает манифест коммита: В оперативной памяти Git склеивает текстовый блок:
    
    - Ссылка на корневое `tree`.
    - Ссылка на `parent` (если это не самый первый коммит).
    - Имя, email и таймстемп автора/коммитера.
    - Твое сообщение коммита (флаг `-m`).
    
4. Считает хэш коммита: От всего этого итогового текста Git рассчитывает SHA-1 хэш. Именно поэтому хэш коммита уникален: если изменить хотя бы одну букву в сообщении или секунду в датe, хэш коммита станет совершенно другим.
5. Записывает коммит на диск: Git сжимает этот текст через zlib и сохраняет как новый файл в знакомую тебе папку `.git/objects/`.
6. Двигает ветку: В самом конце Git берет файл текущей ветки (например, `.git/refs/heads/main`) и перезаписывает в нем старый хэш на только что созданный новый хэш коммита.

## Подтверждение твоей логики

Ты очень точно заметил разделение обязанностей:

- `git add` — это работа с контентом (создание `blob`).
- `git commit` — это работа со структурой и историей (создание `tree` и самого `commit`).

Благодаря этому, если ты сделал `git add`, но передумал коммитить, твои файлы уже «забэкаплены» в базе Git в виде блобов (правда, пока без имени и истории, и со временем их удалит автоматический сборщик мусора, если они так и не привяжутся к коммиту).

## Ветки и HEAD

После всей магии с хэшами, блобами и деревьями, устройство веток и указателя HEAD поражает своей простотой. Физически это обычные, крошечные текстовые файлы, которые можно открыть любым Блокнотом.

Давай разберем их анатомию и то, как они работают «под капотом».
## 1. Что такое ветка (branch) физически?

В Git ветка — это не копия проекта и не изолированная папка. Ветка — это просто именованный указатель (ярлык) на конкретный коммит. [.git/refs/heads/main]

Если ты зайдешь в папку своего репозитория и пройдешь по пути `.git/refs/heads/`, ты увидишь там файлы с названиями твоих веток (например, `main`, `develop`, `feature-1`).

Что внутри этого файла?  
Если открыть файл `.git/refs/heads/main`, внутри будет ровно одна строчка из 41 символа: сорокасимвольный SHA-1 хэш коммита и символ перевода строки. Например:

```text
8a23425118742880029b35b6ab37c9f6d14902b1
```

Этот файл весит ровно 41 байт. Именно поэтому создание новой ветки в Git (`git branch new-feature`) происходит мгновенно: Git не копирует файлы проекта, он просто создает текстовый файлик весом 41 байт и записывает туда хэш текущего коммита.

Когда ты делаешь новый коммит, Git просто перезаписывает эту строчку в файле ветки, вставляя туда хэш нового коммита. Ветка «растет» сама, просто обновляя свой указатель.

## 2. Что такое HEAD физически?

В Git одновременно может быть много веток. Как Git понимает, на какой именно ветке ты сейчас находишься и куда записывать следующий коммит? Для этого используется указатель HEAD.

Физически файл `HEAD` лежит прямо в корне папки `.git/HEAD`.

Что внутри файла HEAD?  
В 99% случаев внутри этого файла записана ссылка на файл текущей ветки. Если открыть его, ты увидишь:

```text
ref: refs/heads/main
```

Это говорит Git: «Мы сейчас находимся на ветке `main`».

## Как работает связка HEAD -> Ветка -> Коммит?

Когда ты делаешь команду `git commit`, Git выполняет простую цепочку:

1. Смотрит в файл `.git/HEAD` и видит там `refs/heads/main`.
2. Идет в файл `.git/refs/heads/main`.
3. Создает новый коммит, делает его родителем тот хэш, который _был_ записан в `main`.
4. Записывает хэш _нового_ коммита внутрь файла `main`.

Сам файл `HEAD` при этом даже не меняется — он как указывал на `main`, так и указывает!

## Что происходит при `git checkout` или `git switch`?

Когда ты переключаешься на другую ветку, например, `git switch develop`, Git делает две вещи:

1. Физически перезаписывает файл HEAD. Теперь внутри него будет написано `ref: refs/heads/develop`.
2. Обновляет файлы в твоей рабочей папке. Git смотрит, на какой коммит указывает ветка `develop`, находит его объект `tree`, достает оттуда блобы и «распаковывает» их на диск, заменяя старые файлы новыми.

## Бонус: Что такое «Состояние отсоединенного HEAD» (Detached HEAD)?

Ты наверняка сталкивался с этим страшным предупреждением от Git. Теперь ты легко поймешь, что оно значит физически.

Если ты переключишься не на ветку, а напрямую на конкретный коммит (например, `git checkout 8a2342`), Git запишет в файл `.git/HEAD` не ссылку на ветку, а хэш коммита напрямую:

```text
8a23425118742880029b35b6ab37c9f6d14902b1
```

Это и называется Detached HEAD. Git предупреждает: «Ты стоишь на коммите напрямую, а не на ветке. Если ты сейчас сделаешь новый коммит, файл HEAD обновится, но ни одна ветка не сдвинется. Твой новый коммит зависнет в воздухе, и на него не будет ссылаться ни один текстовый файл-ярлык».
