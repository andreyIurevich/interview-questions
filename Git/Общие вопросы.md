**Git** - распределенная система управления версиями (VCS).

Распределенная система - каждый разработчик имеет полную копию репозитория (истории проекта) на своем компьютере.

**Staging area (она же index)** — это промежуточный слой между рабочей директорией и коммитом. 
Есть три состояния файлов:
	1. **Working directory (рабочая директория)**  файлы, которые ты редактируешь
	2. **Staging area (index)**  
    → изменения, которые попадут в следующий commit
	3. **Repository (история / коммиты)**  
    → уже сохранённые снимки
Git добавил её, чтобы:
1. Делать **атомарные коммиты** (логически завершённые)
2. Разделять изменения
3. Управлять историей более точно

**Коммит (commit) в Git** — это зафиксированное состояние проекта в определённый момент времени. Проще говоря, это “снимок” (snapshot) файлов, которые ты решил сохранить в истории.

Git:
1. Берёт изменения из **staging area** (то, что добавлено через `git add`)
2. Сохраняет их как новый снимок проекта
3. Добавляет запись в историю

Сам объект коммита — это тоже **простой текстовый файл**, сжатый с помощью zlib. Если его «распаковать», ты увидишь структурированный текст, в котором записано всего несколько строчек:

1. **Ссылка на дерево (`tree`):** Хэш-код главного дерева (корневой папки твоего проекта). Зная этот хэш, Git может восстановить абсолютно все файлы и папки в том виде, какими они были в момент коммита.
2. **Ссылка на родителя (`parent`):** Хэш-код (или коды) предыдущего коммита, на основе которого сделан этот. Так выстраивается история. У самого первого коммита в репозитории этой строчки нет.
3. **Автор (`author`):** Имя, email и точное время (таймстемп), когда код был написан.
4. **Коммитер (`committer`):** Имя, email и время, когда коммит был непосредственно создан (иногда автор и коммитер — это разные люди, например, при применении чужого патча).
5. **Сообщение коммита:** Текст, который ты пишешь после флага `-m`.

Если заглянуть внутрь объекта коммита с помощью команды `git cat-file -p <хеш_коммита>`, ты увидишь примерно следующее:

```text
tree 92a51e6375f4f852b492b3b0dfb2f1532822a16d
parent 5b1a3c8293751283e390df0381023d810f391aef
author Ivan Ivanov <ivan@example.com> 1792156800 +0300
committer Ivan Ivanov <ivan@example.com> 1792156800 +0300

Реализовал авторизацию пользователей
```

Ветка в Git — это простой перемещаемый указатель на один из коммитов.

Если открыть файл `.git/refs/heads/main`, внутри будет ровно **одна строчка из 41 символа**: сорокасимвольный SHA-1 хэш коммита и символ перевода строки. Например:

```text
8a23425118742880029b35b6ab37c9f6d14902b1
```

HEAD - это указатель на текущую локальную ветку.

Если выполняются изменения в одном и том же месте одного и того же файла в разных ветвях одного репозитория, то при попытке объединить эти ветки можно получить **конфликт слияния**.

**Rebase**

Есть основная ветка `master` и есть ветка `experiment`, в которой делаем правки.
Перебазирование этой ветки относительно ветки `master` следующим образом:

```console
$ git checkout experiment
$ git rebase master
First, rewinding head to replay your work on top of it...
Applying: added staged command

$ git checkout master
$ git merge experiment
```

`rebase` берёт коммиты текущей ветки, которых нет в новой базовой ветке, и заново применяет их поверх этой новой базы в том же порядке. 

Команда `git rebase` берет уникальные коммиты ветки `feature` и **последовательно переносит их в конец актуальной истории ветки `main`**. В результате создаются новые коммиты с новыми SHA-хэшами.

---

**Частые вопросы:**

Отличие `git fetch` от `git pull`

git fetch и git pull служат для получения изменений из удаленного репозитория, но делают это по-разному. Fetch только **скачивает** новые данные, не меняя рабочую копию, что безопасно. Pull **скачивает и сразу сливает** (merge) эти изменения в текущую ветку. 

**Основные отличия:**

- **Git Fetch:** Скачивает коммиты, файлы и ссылки из удаленного репозитория, обновляя состояние `origin/master`, но не затрагивает ваши локальные файлы. Позволяет увидеть, что сделали другие, перед тем как объединить изменения.
- **Git Pull:** Это, по сути, комбинация `git fetch` + `git merge`. Она автоматически обновляет локальную ветку.

---

Отличие `merge` от `rebase`

`merge` сохраняет историю и создаёт merge-коммит, а `rebase` переписывает историю, перенося коммиты поверх другой ветки.  
В команде обычно используют `merge`, а `rebase` — для приведения ветки к чистому виду перед слиянием.

---

`Никогда не делай rebase публичной ветки`

Нельзя делать rebase публичной ветки, потому что он переписывает историю и меняет хэши коммитов.  
Если ветка уже запушена и используется другими разработчиками, это приведёт к рассинхронизации и проблемам при pull.

---

Отмена изменений

Как откатить `merge` ветки:
1. Коммит не запушен, команда: `git reset` --hard HEAD~1
2. Коммит запушен, команда: `git revert` -m 1 merge-commit-hash

Параметер `git revert -m 1`

Если ты находишься на `development`

```text
git checkout development
git merge feature
```

получится

```text
development

A -- B -- C -------- M
      \            /
feature D -- E ----
```

Git записывает

```text
parent1 = development (C)
parent2 = feature (E)
```

То есть: **текущая ветка всегда становится первым родителем.**

Это правило Git.

Я бы запомнил это так:

- Обычный коммит → один родитель → `git revert <commit>`.
- Merge-коммит → два родителя → Git спрашивает: **"Относительно какого родителя отменять изменения?"**
- `-m 1` отвечает: **"Считай основной линией истории ту ветку, в которой был выполнен `git merge`."**

```text
// возвращает файл к состоянию последнего коммита, удаляя несохраненные локальные изменения
git checkout -- <имя файла>

// Убрать файл из индекса (но оставить изменения в рабочей области)
git reset <имя файла>

// «Откатить» (reset) ветку к определённому коммиту
git reset --hard <хеш_коммита>

```
