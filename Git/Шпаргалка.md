# 🛠️ Глубокий Git: Физическое устройство и Шпаргалка по отмене изменений

Эта шпаргалка основана на внутреннем устройстве Git. Понимание того, как Git работает на диске, поможет тебе уверенно управлять историей и безболезненно отменять любые действия.

---

## 💾 1. Анатомия Git под капотом (Что происходит на диске)

Git хранит не разницу между файлами (диффы), а **полные слепки (снимки)** проекта в скрытой папке `.git/objects/`.

### Основные объекты Git:
*   **Blob (Блоб):** Физический сжатый файл, содержащий *только контент*. Он не знает своего имени и папки. Его имя — это SHA-1 хэш от содержимого. Если 10 файлов проекта имеют одинаковый текст, Git создаст всего **один** блоб.
*   **Tree (Дерево):** Объект-папка. Хранит список файлов и подпапок: их имена, права доступа и ссылки на соответствующие блобы или другие деревья.
*   **Commit (Коммит):** Крошечный текстовый манифест. Содержит ссылку на корневое дерево (`tree`), ссылку на предыдущий коммит (`parent`), автора, дату и сообщение коммита.
*   **Ветка (Branch):** Простой текстовый файл в `.git/refs/heads/имя_ветки` весом всего **41 байт**. Внутри записана ровно одна строчка — хэш последнего коммита. Создание ветки происходит мгновенно.
*   **HEAD:** Указатель в `.git/HEAD`. Обычно содержит ссылку на текущую активную ветку (например, `ref: refs/heads/main`).
*   **Индекс (`.git/index` или Staging Area):** Бинарный файл-кэш. Содержит плоский список всех файлов проекта, хэши их блобов и метаданные ОС (время изменения `mtime`). Благодаря ему `git status` работает мгновенно, не пересчитывая файлы заново.

## 🧯 2. Шпаргалка по отмене изменений

| Команда | Зона ответственности | Изменяет ли историю? | Безопасность |
| :--- | :--- | :--- | :--- |
| **`git restore`** | Восстановление содержимого *файлов* (в индексе или рабочей папке). | **Нет** (указатели веток не двигаются). | Безопасна для графа коммитов. |
| **`git reset`** | Управление *историей* (перемещение указателя ветки `HEAD` в прошлое). | **Да** (меняет положение текущей ветки). | Требует осторожности, особенно с флагом `--hard`. |

### Уровень 1: Код только в редакторе (Красный в `git status`)
*   `git restore <имя_файла>` (или старая `git checkout -- <file>`) — Стереть изменения в файле, вернув его к состоянию последнего коммита.
*   `git restore .` — Отменить изменения во **всех** файлах текущей папки.
*   `git clean -fd` — Физически удалить с диска все неотслеживаемые (untracked) новые файлы и папки.

### Уровень 2: Файлы добавлены в индекс через `git add` (Зеленый в `git status`)
*   `git restore --staged <имя_файла>` — Убрать файл из индекса. Код внутри файла на диске **не меняется** (он просто снова становится «красным»).
*   `git restore --staged .` — Сбросить из индекса сразу все подготовленные файлы.

### Уровень 3: Коммит сделан локально (Push еще НЕ делали)
*   `git commit --amend -m "Новый текст"` — Перезаписать самый последний коммит (исправить опечатку или добавить забытые через `git add` файлы). Старый коммит отвязывается, создается новый.
*   `git reset --soft HEAD~1` — **Самый безопасный сброс.** Удаляет последний коммит, но **сохраняет весь код**. Изменения возвращаются в индекс (становятся «зелеными»).
*   `git reset --mixed HEAD~1` (или просто `git reset HEAD~1`) — Удаляет коммит, код остается на диске, но изменения вылетают из индекса («краснеют»).
*   ⚠️ `git reset --hard HEAD~1` — **Опасная команда.** Полностью уничтожает последний коммит, очищает индекс и физически стирает файлы этих изменений с диска.

### Уровень 4: Коммиты уже отправлены на сервер (`git push` выполнен)
*   `git revert <хэш_коммита>` — **Единственный безопасный способ для общих веток.** Git анализирует изменения старого коммита и создает **новый коммит-выворот** (делает всё наоборот). История не переписывается, коллеги не пострадают.

## 🪵 3. Спасение «удаленных» коммитов через `git reflog`

Если ты случайно сделал жесткий сброс (`git reset --hard`) или перезаписал коммит через `--amend`, данные всё еще лежат в базе `.git/objects/`. Они удалятся сборщиком мусора только через несколько недель.

### Алгоритм восстановления:
1. Выведи историю перемещения указателя HEAD:
   ```bash
   git reflog
   ```
2. Найдите строчку, описывающую состояние проекта *до* роковой ошибки. Скопируй сорокасимвольный хэш коммита (например, `e5f6g7h`).
3. Верни ветку на этот коммит:
   ```bash
   git reset --hard e5f6g7h
   ```

## 🔀 4. Правильный и безопасный Git Rebase

**Определение:** Команда `git rebase dev` берет уникальные коммиты текущей ветки (`feature`), временно откладывает их, сдвигает точку разветвления (основание) к самому свежему коммиту базовой ветки (`dev`), а затем последовательно применяет патчи изменений заново. На выходе создаются **новые коммиты с новыми хэшами**.

### ⚠️ Золотое правило Rebase:
> **Никогда не делай rebase публичной ветки!**
> Если ветку `feature` скачал хотя бы один твой коллега, после твоего ребейза и форсированного пуша его Git сойдет с ума, пытаясь соединить старые коммиты с новыми. Это приведет к каше в истории и дубликатам кода.

### 🛡️ Сценарий: Безопасное обновление своей локальной ветки (если работаешь один)

Когда коллеги напринимали коммитов в `dev`, а тебе нужно обновить свою ветку `feature`:

1. Обнови локальную копию общей ветки:
   ```bash
   git checkout dev
   ```
   ```bash
   git pull origin dev
   ```
2. Вернись в свою ветку:
   ```bash
   git checkout feature
   ```
3. Смени основание ветки (накати свежий код из `dev` под свои коммиты):
   ```bash
   git rebase dev
   ```
   *(Если возникнут конфликты, исправь файлы, сделай `git add <файл>` и продолжи через `git rebase --continue`)*
4. Отправь обновленную историю на сервер с умной защитой:
   ```bash
   git push origin feature --force-with-lease
   ```
   *Флаг `--force-with-lease` заблокирует пуш, если кто-то другой успел отправить новые коммиты в твою ветку на сервере, защищая тебя от затирания чужой работы.*
